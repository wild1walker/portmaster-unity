# Runtime reference

`ua_host <root>` runs a game with Unity's ARMv7 Android player. `<root>` holds:

| path | what |
|---|---|
| `lib/libmain.so`, `lib/libunity.so`, `lib/libmono.so` | the player (Release variant; `UA_LIBDIR` for another folder, e.g. the Development player) |
| `<name>.apk`, `main.<code>.<package>.obb` | the game's data, from `pmunity android-data --pack all` |
| `android_package.json` | written beside the APK by the data tool: package, build id, APK name, Unity version (read by ua_host) |
| `assets/bin/Data/Managed/etc/` | Mono's config, read relative to the working directory (the data tool's zip folder has it) |
| files the game reads beside its data | e.g. a GOG build's `goggame-*.info` (`--beside`) |
| `plugins.map` | written beside the APK by the data tool: what each native library the game P/Invokes becomes (ARM build in `lib/`, system library, built-in stub, refused) and the float signatures of glibc plugins ([plugins.md](plugins.md)) |
| `lib/<plugin>.so` | ARM builds of the game's plugins (FMOD's Android libraries, ...) beside the player |
| `assets/*.bank` | FMOD banks, kept out of the OBB (FMOD opens them as files) |
| `Game_Data/StreamingAssets/` | StreamingAssets as plain files, for code that reads them with System.IO (`android-data --streaming-assets both\|loose` with asmpatch's streaming-assets patch; android-data.md section 6) |
| `data/` | created: `files/`, `cache/` (Unity's shader cache, temporaryCachePath), `external/` (persistentDataPath: saves), `shared_prefs/` (PlayerPrefs, `<package>.v2.playerprefs.prefs`; `pmunity prefs` converts it to and from a Linux player's `prefs`) |

What the host answers for itself (besides the Android shims): `System.loadLibrary(name)` /
`UnityPlayer.loadLibrary(name)` load `lib<name>.so` from the library folder and `System.load(path)`
that file, with the library's `JNI_OnLoad` called the first time (runtime/host/ua_host.c); and
`libsteam_api.so`, unless the library folder has a real ARM one, is a stub of the Steamworks flat
API that answers as a PC without a running Steam client (Init fails, the game goes on without
Steam; runtime/host/steamstub.c; `STEAMSTUB=0 runtime/host/build.sh` builds a ua_host without it and
without the old Steamworks.NET stub, for games that do not use Steamworks). The game's other native plugins follow `plugins.map`
([plugins.md](plugins.md)): ARM builds in `lib/`, the system's libraries, built-in stubs of
platform SDKs (Discord, EOS, old Steamworks.NET), a silent Wwise made of the game's own entry points
(runtime/host/wwise.c, [plugins.md](plugins.md#wwise)), or refused. Android system properties come from the loader
(`SO_PROP_<name, '.' as '_'>` overrides them; `swappy.disable=1` keeps Android Frame Pacing off).

Run it with the 32-bit libraries first: `LD_LIBRARY_PATH=/lib32:/usr/lib32 ./ua_host "$PWD"`
(`tools/device/run.sh` does that, silent by default). Pads: SDL2 GameController, mapped by
`SDL_GAMECONTROLLERCONFIG` (PortMaster's launchers set it through `get_controls`).

## Display

`ua_host` picks the EGL window Unity draws into before it starts Unity (`runtime/host/display.c`):

| `UA_DISPLAY` | what |
|---|---|
| `auto` (default) | `fbdev` when the framebuffer (`ANDROID_FBDEV`, default `/dev/fb0`) exists and libEGL is an fbdev-only one: no window-system platform (`EGL_*_platform_gbm/wayland/x11/xcb/device/surfaceless`) in its client extensions, which Mesa and the Wayland/GBM/X11 flavors of vendor drivers always list. Otherwise `sdl`; if SDL cannot open a GLES window, `fbdev`. The choice and the reason are logged (`[display] auto: ...`) |
| `fbdev` | Mali's fbdev EGL (Knulli on the Allwinner H700): no window system is probed; the framebuffer's buffers and the flips are the host's (below) |
| `sdl` | an SDL2 window (Wayland, KMSDRM, X11 through EGL, SDL's offscreen driver; `SDL_VIDEODRIVER` picks one) whose EGL display, config and window surface Unity is given (`runtime/android/README.md`, "Host display"); stops if SDL cannot open one |

With `UA_EGL_PBUFFER=1` (tests on Mesa's surfaceless platform) the fbdev code path is always taken.

### The fbdev path's flips

Mali's fbdev EGL draws the window into the framebuffer itself and shows a finished frame by panning
to it (`FBIOPAN_DISPLAY`). On the RG34XX-SP (sunxi's fbdev, Mali-G31 r20p0) the pan returns at the
vblank that shows the frame, whatever `eglSwapInterval` says, and the driver makes it on the thread
that also feeds the GPU (`mali-cmar-backend`): while it waits, the GPU gets no work. A frame of 18 ms
of GPU work was shown every second refresh (30 fps), the GPU idle a third of the time and clocked
down for it (simple_ondemand: 420 - 504 MHz, at times 336 MHz and 20 fps); a third buffer alone
changed nothing (Cell Machine 29.7 fps with 2 or 3). So ua_host makes the flips
(`runtime/host/fbdev.c`): it exports `ioctl`, the driver's pans come to it and are queued to a thread
of the host (`ua_flip`) that makes them in order, and the driver's call returns at once; the screen
info the driver reads before each pan is answered from the host's copy (the kernel would answer only
once a pending pan is done: its fb lock). The driver takes the return as "shown" and hands the buffer
shown before to the next frame, so the framebuffer gets four buffers (its virtual height; the
RG34XX-SP's framebuffer memory holds five 720x480 screens; the old geometry is put back when ua_host
ends, by a small watcher process, `ua_fbrestore`, if ua_host is killed) and Unity's render thread
waits after each `eglSwapBuffers` until the buffer its next frame draws into has really left the
screen (the driver uses its buffers in turn). Nothing the GPU draws into is on the screen, every
frame is shown at a vblank, in order: no tearing (`runtime/host/test/fbdev_test.sh`: a fake driver
and display; without the wait the same scenarios tear).

On the RG34XX-SP (fps, then the time from a frame's swap to its flip):

| game | driver's flips (before) | host flips | without vsync (`mailbox`, tears) |
|---|---|---|---|
| Cell Machine (2019.3, URP), level 1 | 29.7, 31 ms | **53.6**, 25 ms | 53.4 |
| Chapéu de Papel (2022.3 macOS, URP), title | 20.2 - 29.6 (GPU at 336 or 600 MHz), 90 ms | **36.4**, 73 ms | 36.3 |
| Hollow Knight 64-bit (6000.0), main menu | 38.2, 23 ms | **42.6**, 28 ms | |
| The Third Eye (2022.2, URP 3D), first scene | 29.6, 26 ms | 31.9, 27 ms | |
| White Mirror (2021.2, URP), in game | 43.0 (197 frames over 25 ms in 25 s), 35 ms | 43.1 (12), 36 ms | |
| Chapéu de Papel APK (IL2CPP arm64), first scene | 32.9, 31 ms | 33.4, 31 ms | |
| Cuphead 64-bit (2017.4 IL2CPP), title | 59.4, 45 ms | 59.4, 28 ms | |
| Tom City (2020.3), title | 59.3, 47 ms | 59.4, 30.5 ms | |

Games the GPU limits gain what the wait for the vblank cost (the GPU now at 696 MHz throughout;
those already at it gain little). Frames that keep up with the refresh are shown a refresh sooner
than with the driver's own flips (it queued swapped frames on its thread); frames the GPU is late
with keep two queued, so the GPU always has the next one (a few ms more from swap to screen than
the driver's flips in Hollow Knight's menu, at 11 % more frames).

| variable | effect (fbdev) |
|---|---|
| `UA_FB_FLIP=host\|driver\|mailbox` | `host` (default): the flips above; falls back to `driver` with fewer than three buffers or when the driver does not use its buffers in turn. `driver`: the driver's own pans (the old behaviour). `mailbox`: a measurement, tears: the driver's pan returns at once and only the newest frame is flipped to, so the frame rate is what the frames cost (above the refresh rate when they cost less); `UA_SWAP_INTERVAL=0` changes nothing on this driver |
| `UA_FB_BUFFERS=<n>` | the framebuffer's virtual height as `n` screens, when its memory holds them. Default: 4 with host flips (3 if the memory holds no more), else the firmware's (2 on Knulli) |
| `UA_FB_QUEUE=<n>` | frames the render thread may be ahead of the screen, at most buffers - 2 (and 2). Default: automatic, 2 while frames miss refreshes (the GPU always has the next frame), 1 once 30 frames in a row were done while the one before still waited for its flip (the game keeps up with the refresh, and a second queued frame would only be latency); back to 2 at a missed refresh, for 2 s (doubling up to a minute at each fall-back, so a game at the edge does not go back and forth) |
| `UA_FB_TRACE=<n>`, `UA_FB_TRACE_START=<s>` | `[fbtrace]` lines: the times of `n` swaps, the driver's pans and the flips, from `s` (40) seconds after the first swap |
| `UA_RENDER_SIZE=<w>x<h>`, `UA_RENDER_SCALE=<s>` | (off by default: a visual setting) Unity's window at that size, smaller than the panel, and the display engine's scaler draws it over the whole panel at no GPU or CPU cost (below). The size keeps the panel's aspect and is even (720x480: 660x440, 630x420, 600x400, 576x384, 540x360, ...); a size of another aspect becomes the largest of the panel's aspect within it, a scale the nearest such size; a quarter of the panel at least. Logged as `[fbdev] render size ...`. The display engine's scaler is Allwinner's (`/sys/class/disp`, e.g. H700); on other framebuffers (Rockchip's would show the smaller window shifted) and on the SDL path (a window under Wayland, KMSDRM, X11) Unity is told the smaller size and the GPU scales its frame up to the panel or window before each swap (two framebuffer blits; GLES 3; logged as `[display] render size ...`), which costs a little GPU time where the display engine's costs none. `UA_RENDER_SCALER=display|gpu` overrides the choice |
| `UA_ASPECT=<w>:<h>` | (off by default) the picture keeps that aspect on a panel of another one: Unity's window gets the largest even size of the aspect inside the panel, with black bars. On the fbdev path with bars above and below (a panel narrower than the aspect) there is no copy: Unity draws into the bottom lines of a surface of the bar above plus the picture, so the picture lands in the middle of the panel; the driver is told that height as the screen's, so its buffers lie that far apart and more of them fit in the framebuffer's memory (720x720 at 16:9: 4 buffers 562 lines apart instead of 3 screens, and so two queued frames: 40 -> 49 fps in a 2017.4 game's heaviest scene on an H700 handheld). Otherwise the GPU copies the frame into the middle (`UA_ASPECT_COPY=1` chooses it). For a game composed for one aspect whose player asks for a smaller window anyway (`defaultIsNativeResolution` off: 16:9 on a 720x720 panel would be stretched by the display engine). Nothing changes on a panel of that aspect. `UA_RENDER_SIZE` / `UA_RENDER_SCALE` then pick within that size, and the GPU scales up to it. The no-copy path ran on an H700 handheld (Mali-G31, fbdev); the copy in `display_test.sh` only |
| `UA_RENDER_RAM=<MB>` | the render size only on a device with at most that much memory (`MemTotal`): e.g. `UA_RENDER_SIZE=600x400 UA_RENDER_RAM=1024` in a port's launcher softens the picture on 1 GB handhelds and leaves larger ones at the panel's size |
| `UA_PRESENT_THREAD=1` | (SDL path with a render size, no `UA_ASPECT`, SDL's KMSDRM or X11 driver (Wayland not yet checked); off by default) Unity's frames shown by a present thread of the host's: Mali's GBM driver (RK3326 handhelds: BattleXP G350, R36S class; r13p0, SDL's KMSDRM) waits in eglSwapBuffers until the GPU has finished the frame, so Unity's render thread waited for the GPU at every swap and the GPU for the render thread while it built the next frame. With it, Unity's contexts are current without a surface (`EGL_KHR_surfaceless_context`) and Unity's framebuffer 0 is one of three framebuffers of the host's at the render size (one depth-stencil renderbuffer for all); binding 0 binds the current one, and what Unity reads about framebuffer 0 reads as before (the binding as 0; `GL_BACK`/`GL_DEPTH`/`GL_STENCIL` in invalidations, draw/read buffers and attachment queries). At Unity's swap the render thread fences the frame and goes on with the next frame (waiting on the GPU, not the CPU, until the copy of the one before is done); the present thread, with a context sharing Unity's, waits for that fence on the GPU, scales the frame over the window in one linear `glBlitFramebuffer` (one pass fewer than the GPU scaler's copy and scale) and swaps. Unity may run up to two frames ahead of the screen (as the fbdev path's queue). Screenshots, the on-screen keyboard and the cursor draw into Unity's frame as before; with it on, each screenshot also saves what the window showed after the scaling (`wshot-<n>.ppm` beside `shot-<n>.ppm`, the window's size). G350, Hollow Knight's Greenpath at 480x360 on the 640x480 panel: 17.5 -> 25.1 fps, stalled 1-second windows 48 -> 1; King's Pass 32 -> 38. `display_test.sh` checks it on Mesa (SDL 2.0.10 and 2.26, X11: every frame read back and shown, the window's picture). runtime/host/glpresent.c |

`UA_FPS`'s lines end with, on the fbdev path, the time from each swap to the flip that shows it
(`shown <avg> / <worst> ms after the swap`), the buffers, the queue depth allowed and the render
thread's wait for its next buffer (`gate`).

### A smaller window, scaled by the display engine (`UA_RENDER_SIZE`)

Mali's fbdev driver draws a window smaller than the framebuffer into the top left of each buffer,
at the framebuffer's pitch, the buffers still a screen apart, and pans with the framebuffer's own
size. sunxi's fbdev (the Allwinner BSP kernel Knulli, muOS and the stock firmware run on the H700)
takes a pan's `xres`/`yres` as the display layer's source crop and keeps the layer's screen window
at the panel's size. With `UA_RENDER_SIZE` the host makes every pan with the window's size, and the
display engine's scaler draws the window over the whole panel: no GPU pass, no CPU work, no
latency. Checked on the RG34XX-SP with a test program (now `runtime/host/egltest <s> <w>x<h>`: a
still pattern in a smaller window, the pans made with its size) and the display engine's own
capture of what it sends to the panel (`echo <file>.bmp > /sys/class/disp/disp/attr/capture_dump`; `cat
/sys/class/disp/disp/attr/sys` lists the layer's `crop[...]` and `frame[...]`): 540x360 and 600x400
fill the 720x480 panel, the 1-pixel border at its edges, nothing sheared. A profbench plan's `cap`
step saves that capture (`cap-<n>.bmp`); `shot` still saves the frame Unity drew, at the render size.

What has the render size: the ANativeWindow and everything the host answers from its size (the EGL
surface, so `Screen.width`/`height`; DisplayMetrics, `Display.getWidth`/`getRealMetrics` and its
mode's size, the View, the AConfiguration's dp size), pointer mode (cursor, speed, `ptr=` pixels; fractions are the same
point on the screen), the on-screen keyboard and screenshots. The game draws its frame, its UI
included, at that size, and the panel shows it scaled: the picture is softer, which makes it a
visual setting, never a default for every port. A game that sizes its view in pixels (a pixel-perfect
camera, a zoom picked from `Screen.height`) could show more or less of a level at another size:
compare `shot` screenshots of one scene at both sizes before turning it on for a port
([profiling.md](profiling.md#rendering-smaller-the-display-engines-scaler-ua_render_size)).
Resize requests stay inside the window: `SurfaceHolder.setFixedSize` is a no-op as before, and an `ANativeWindow_setBuffersGeometry` larger than
the window is cut to it, side by side (Mali refuses a window larger than the framebuffer's screen:
`eglCreateWindowSurface` fails with `EGL_BAD_NATIVE_WINDOW`); a smaller one is scaled to the panel
the same way (the pans carry the size of whatever window the driver draws). The crop is put back to the whole screen when the host ends, after a crash, and by
`ua_fbrestore` if the host is killed. URP's own render scale (`m_RenderScale`, a converter setting)
multiplies with it: the URP camera renders at its scale of the window.

| `UA_MONO_OPTIONS` | Mono options; `--trace=T:Class,M:Class:Method` (no `<` in specs) |
| `UA_MONO_TRACE` | log Mono class/method/field lookups that fail |
| `FJ_TRACE` | log every JNI call |
| `ANDROID_SLES_OUTPUT` | `auto` (SDL, else pipe), `sdl`, `pipe`, `none`; `ANDROID_SLES_PIPE_CMD` overrides the client. `none`: no output, no device, no process; each player's buffers are taken on the clock as a sound card would and dropped, so the game's mixer and the Wwise player work as with sound (tools/device's silent runs set it with `SDL_AUDIODRIVER=dummy`). `auto` never takes the pipe when the run asked for SDL's dummy driver (silence) and this SDL cannot start it (muOS's 32-bit SDL has none): it is `none` then (`OpenSL: SDL_AUDIODRIVER=dummy was asked for (silence) and this SDL cannot start it: no output, as ANDROID_SLES_OUTPUT=none (never the pipe)`). The pipe goes to `pw-cat` (PipeWire), else `pacat` (PulseAudio), else the system's `aplay` (ALSA alone, e.g. when the 32-bit alsa-lib cannot drive an older kernel). A 32-bit SDL that cannot start any audio driver (muOS's has no `dummy`) no longer leaves the game silent: with `auto` or `pipe` the engine starts without it and the players use the pipe (`OpenSL: no SDL audio: the players use the pipe output`), unless the dummy driver was asked for (above). The pipe's writer runs at the priority SDL gives its own audio thread (nice -20, which root may set; `ANDROID_SLES_PIPE_NICE=<n>` another, `0` the game's own, for measurements): the pipe holds 21 ms at 48 kHz, 43 ms at 24 kHz, and at the game's priority a burst of its threads kept the writer away for up to 54 ms in a Docker test with 24 busy threads on 4 CPUs, none at nice -20. The writer takes the game's buffers on the clock, as a sound card does (a write's worth per its time, at most twice as fast while the pipe is below 3/4 full): taken as fast as the pipe had room, a writer back from a stall or a client reading in bursts took the game's whole queue at once, before Unity's FMOD (which fills a buffer from what its mixer thread, awake every 10 ms, has mixed) had refilled it, and the buffers went out again with their old contents: on a Knulli RG34XX-SP in King's Pass 20-80% of them each second, the four-buffer queue (85 ms at 24 kHz) heard twice over; the SDL output, a steady pull, had none, nor has the paced pipe. An empty pipe with the writer more than a write late (a gap once the client's own buffer runs out too) is logged as underruns are (`OpenSL: pipe ran dry <n> at <s> s (the writer <ms> ms late)`) |
| `ANDROID_SLES_CAPTURE=<file>` | each OpenSL player also writes what it outputs to `<file>` (raw PCM in the player's format, a gap as silence; a later player to `<file>.<n>`): a silent device test can check the sound itself. Independently, every underrun (the game's mixer let the queue run dry, a gap the listener hears) is logged with its length at the time since the first frame, as `[hitch]` lines are (`OpenSL: underrun <n>: <ms> ms of silence at <s> s`; the first 50, then every 100th) |
| `ANDROID_SLES_APLAY_DEVICES` | the ALSA devices the `aplay` client tries in order (default `plughw:0,0 default`: the card directly, without dmix's buffer, else the system's default device when the card is busy) |
| `UA_SHADER_DUMP=<dir>` | write every GLSL source Unity compiles to `<dir>/<fnv64>.glsl` (runtime/host/glhooks.c) |

| `UA_HTTP=1` | Unity 2017.4 - 2018.4: UnityWebRequest/WWW make real requests through the system's libcurl (default: they fail at once, as without a network; [plugins.md](plugins.md#https)) |
| `UA_AUDIO_RATE`, `UA_AUDIO_FRAMES` | output rate and buffer size AudioManager reports to FMOD (default 48000, 512; empty or out of range: the default). `UA_AUDIO_RATE=24000` is a 1 GB trade-off a port may set in `[runtime_lowmem]`: FMOD mixes and runs its effects at half the rate (duller highs, the same sounds at the same times), its mixer 48 -> 31 % of a core in Hollow Knight, which on a shared power budget leaves the Mali more clock (King's Pass walking and fighting with `ASMPATCH_HK_BLUR=off`: 48 -> 54 - 56 fps, [compat/games.md](compat/games.md)). `UA_AUDIO_FRAMES` is for measurements: with `UA_AUDIO_FRAMES=1024` Unity 6000.0's FMOD (Hollow Knight) leaves OpenSL ES for its AudioTrack output, which runs at 24 kHz (`FMODAudioDevice: rate 24000, block 512 frames x 4` in the log): not a longer buffer but half the sample rate ([profiling.md](profiling.md#fmods-mixer-and-the-audio-step-2026-10-24)) |
| `UM_TRACE`, `UM_VIDEO_BUFFERS`, `UM_VPX_THREADS`, `UM_H264`, `UM_FFMPEG` | video (Unity's VideoPlayer, `runtime/media`): per-buffer log with each line's time (`CLOCK_MONOTONIC` ms: decodes, the output buffers Unity dequeues and releases, each `updateTexImage`), a video decoder's output queue (default 4), libvpx threads (VP8 one by default: its threads spin waiting for each other), OpenH264 for every H.264 stream, the system's libavcodec off / from a path (see Video below) |
| `UA_VIDEO_RATE=game` | keep the game's frame rate while a video plays. By default desktop pacing (`UA_FRAME_RATE=desktop`) gives at least the display's rate while a picture was latched in the last half second: Unity 6000's SurfaceTexture video path keeps one picture in flight and shows at most half the game's frame rate, and Hollow Knight paces its 30 fps cinematics at 30 (`[host] frame rate 60 fps (... a video on the screen)`). With clips small enough to decode in time (convert's `video` step on 1 GB handhelds) the cinematics then show their 30 pictures a second; a 1080p clip whose decoding is the limit shows fewer with more game frames ([runtime/media/README.md](../runtime/media/README.md#unity-6000-one-picture-in-flight)) |
| `UA_HITCH_TRACE=<ms>` | in frames longer than `<ms>`, sample `UA_HITCH_THREADS` (default `UnityMain`) every `UA_HITCH_EVERY` ms (20): pc, lr, return addresses as module+offset (runtime/host/hitches.c; `tools/analysis/sym.py` names libunity offsets, `tools/analysis/hitchsum.py` sums them up). `UA_PROF_EVERY=<ms>` logs such a sample of those threads every `<ms>` all the time (`hitchsum.py --prof`; heavy: `UA_PROF` replaces it) |
| `UA_PROF=<hz>` | the sampling profiler, off by default: recordings of `UA_PROF_THREADS` (default `UnityMain,UnityGfxDeviceW`; `Job.Worker*` style prefixes, `@swap` the presenting thread) at `<hz>` samples a second, `UA_PROF_SECS` long (20), started by `touch <root>/prof.req` (a number in it: the length) or once `UA_PROF_START` s after the first frame; `UA_PROF_DEPTH` (32) return addresses a sample from `UA_PROF_SCAN` bytes of stack (16384). Each one is written to `<root>/prof-<n>.txt`: states (on a CPU, runnable, blocked in which call), pc, lr and callers (unwound through code with unwind tables, scanned above Mono's JIT frames), Mono's JIT methods by name, per-thread CPU time, frame times; `tools/analysis/profsum.py` sums it up by module, function and managed method (runtime/host/prof.c, [profiling.md](profiling.md)) `UA_PROF_EVENT=<event>` samples on a CPU event instead of time (the kernel's PMU through perf_event_open, user code only): a sample every `UA_PROF_EVENT_PERIOD` (10000) occurrences on each sampled thread, e.g. `l2d_cache_refill`, `l1d_cache_refill`, `l1d_tlb_refill`, `bus_access` (the names in `/sys/bus/event_source/devices/*/events`, or `raw:0x<n>`); `profsum.py` then ranks functions by that event (only running threads are sampled) |

## What a desktop game sees

Some answers of Unity's Android player differ from a desktop player's in ways desktop code does not
expect; ua_host gives the desktop's (runtime/host/desktopenv.c; Mono players, and for `Screen.resolutions`
the 64-bit player too: IL2CPP, or Unity's Mono behind the bridge of [mono-arm64.md](mono-arm64.md)):

| | the Android player | ua_host |
|---|---|---|
| `Environment.GetCommandLineArgs()`, `Environment.CommandLine` | libunity gives Mono no main arguments (none to `mono_unity_runtime_set_main_args` / `mono_runtime_set_main_args`), so the list is null and `CommandLine` throws `ArgumentNullException` (`String.Join` of null): a game that looks for its switches stops there (a 2017.4 game's options loader stopped half way) | a desktop player's shape: the program's path (`ua_host`'s), then Unity's own switches (`UA_UNITY_ARGS` and what the host adds to them) or the arguments libunity passes; logged as `[host] the game's command line: ...` |
| `Path.GetTempPath()` | Mono: `$TMPDIR`, else `/tmp`; IL2CPP: `$TMPDIR`/`$TMP`/`$TEMP`, else Android's `/data/local/tmp`, missing on a handheld (Enter the Gungeon's saves, written through `Path.GetTempFileName`, failed on IL2CPP) | `TMPDIR=/tmp` when none of the three is set: Mono's own answer, for both runtimes |
| `Screen.resolutions` | empty (Unity reads display modes only from Android 6's `Display.Mode`): code that indexes it throws (`ArgumentOutOfRangeException` from an options menu's resolution list) | when Unity's list is empty, one mode: the window's size (what `Screen.width`/`height` say) at the display's refresh rate, as a desktop with one mode; Unity's own list is passed through when it has one. Logged once as `[host] Screen.resolutions: ...` |

IL2CPP players keep an empty argument list rather than none (`CommandLine` is "", nothing throws).
On the 64-bit player the host wraps the icall as libunity registers it with `il2cpp_add_internal_call`
and makes the array with the `il2cpp_*` functions libunity looks up (Enter the Gungeon's options code
threw `IndexOutOfRangeException` from `GameOptions.GetRecommendedResolution` there without it).
Checked by `runtime/host/test/plugins_test.sh` (`test_desktopenv`: stand-ins for Mono's setter, its
icall registration and arrays, and for IL2CPP's).

## Video

Unity's VideoPlayer plays clips through `runtime/media` (details, call sequences and costs:
`runtime/media/README.md`): players 2017.4 - 2021.3 through the Java classes of
`runtime/jni/up_media.c`, 2022.3 through `runtime/android/media_ndk.c`. The data needs
`Hidden/VideoDecodeAndroid`, which `pmunity android-data` adds (`docs/android-data.md`).

| clips (desktop build) | picture | sound |
|---|---|---|
| VP8 / VP9 + Vorbis / Opus WebM (Linux builds) | libvpx, built in | libvorbis / libopus, built in |
| H.264 + AAC MP4 (macOS, Windows builds) | OpenH264, built in (with B-frames: the system's libavcodec when there is one, exact; else OpenH264, close) | the system's libavcodec; without it silence |
| HEVC, MP3 | the system's libavcodec | the system's libavcodec; MP3 without it: silence |

At start the log names the decoders (`[media] decoders: vp8 (libvpx-vp8), ...`); each clip logs its
tracks and decoders. `umbench <file> [offset size]` (`runtime/media/out/umbench`, a device check)
decodes a clip as fast as it goes and prints the cost per frame.

Profiling on the device (`UA_PROF`, the bench `tools/device/profbench.sh`): [profiling.md](profiling.md).
Debugging on the device: `python3 tools/device/stacks.py <pid> [thread]` (each thread's syscall and the
libunity return addresses on its stack; name them with `tools/analysis/sym.py`), and gdb attaches to the
32-bit process (`set arm force-mode arm`, `break *<libunity base + offset>`).
